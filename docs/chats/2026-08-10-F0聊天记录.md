## 二、PXSCH_TX_Bit_Processing_Top 核心结论

### 1. 模块定位

- 模块文件：`u7_chip2chip_base.srcs/sources_1/imports/new/PXSCH_TX_Bit_Processing_Top.v:25-211`。
- 实例化位置：`TX_BIT_Processor.v:142-157`。
- 当前发送链给它的是 `PDSCH_transmitter_trigger`，因此当前用途为下行 PDSCH。
- 模块不是单独的 Turbo 编码器，而是“MAC 串行 payload bit → 信道编码 → 加扰 → 调制符号”的编排顶层，同时独立延迟 OFDM-symbol trigger。

### 2. 输入输出的重要语义

- `MCS_data/MCS_valid` 的名称容易误导；它们实际是 MAC 输出的串行 payload bit 及其有效信号，不是 MCS 配置参数。
- `ready_for_input` 来自信道编码链的 `ready_for_data`，反馈给 `MAC_TX.ready_for_output`，只表示编码链能否继续接收 payload bit。
- `symbol_real/symbol_imag` 为 Q2.14 格式复数调制符号，`symbol_valid` 与其同步。
- `delay` 的单位是基带时钟周期；当前上层传入 `ENCODE_SAFE_VALUE=20000`。
- 顶层端口名为 `clk_192M`，但上层实际连接 `clk_baseband`；在检查时钟产生模块前，不能只凭端口名断言频率。

### 3. 配置锁存与启动时序

设原始 `PXSCH_transmitter_trigger` 在 T0 到达：

- T0 锁存 `modulation`、`subframe_index`、`transblock_size` 和 RE 数；
- trigger 延迟 1 拍；
- T1 同时送到 `PXSCH_Channel_Encoder.configuration_valid_in` 和 `PXSCH_Deserializer_Scrambler_Modulator.new_control_pulse`。

这一拍的作用是保证子模块启动时已经看到稳定配置，不应解释成对复杂组合逻辑的流水切分。

### 4. 信道编码调用链

```text
PXSCH_Channel_Encoder
├── PXSCH_Parameter_Computation：按 TBS 查参数表
├── CRC_Add_and_CB_Segmentation：TB/CB CRC 与码块分段
├── Turbo_Encoder_Top：1/3 母码率 Turbo 编码
└── TX_Rate_Matcher：交织、循环缓冲区读取与速率匹配
```

### 5. 速率匹配长度的关键校正

当前 `PXSCH_Channel_Encoder.v` 中，`modulation`、`number_of_REs` 和 `redundancy_version_index` 只出现在端口声明，没有进入参数计算或速率匹配实例。`PXSCH_Parameter_Computation` 仅根据 `transport_block_size` 硬编码查表得到 C、E、K、k0 等参数。

总 coded-bit 数应为：

```text
G = 所有码块 E 的总和
若各码块 E 相同：G = C × E
调制符号数 = G ÷ Qm
QPSK：Qm=2；16QAM：Qm=4
```

对 `TBS=30576`：

```text
C = 5
E = 12480 bit/code-block
G = 5 × 12480 = 62400 coded bit
16QAM符号数 = 62400 ÷ 4 = 15600 symbol
```

旧解释中的 `62400×5` 重复乘了码块数，已校正；原先由此得到的末符号周期估算无效。

### 6. TBS=15840 的歧义

`TBS=15840` 同时被用于：

- 子帧0、`MCS_control=2`，需要 10800 个 QPSK RE；
- 非0子帧、`MCS_control=1`，配置为 15600 个 RE。

当前参数表只按 TBS 查找并采用 `C=3、E=7200`：

```text
G = 3 × 7200 = 21600 bit
QPSK symbol = 21600 ÷ 2 = 10800
```

这对第一种场景闭合，但对非0子帧少 4800 个 QPSK RE。源码中存在被注释掉的 `E=10400` 版本，`3×10400=31200 bit`，恰好对应 15600 个 QPSK RE。由于当前模块不使用 RE 数，无法自动区分两个场景，需进一步修正或验证设计意图。

### 7. 加扰、bit聚合和调制

`PXSCH_Deserializer_Scrambler_Modulator` 的结构为：

```text
coded bit 固定延迟33拍
→ 每Qm个bit组成一个调制字
→ PDSCH加扰
→ LTE星座映射
```

当前工程的扰码初值实现为：

```text
c_init = cell_ID | (RNTI << 14) | (subframe_index << 9)
```

不能再将整个模块简单写成“每个 bit 固定37拍后变成 I/Q”：输入为 coded bit，输出为 modulation symbol，聚合等待与 Qm 有关；当前结构还包含 33 拍输入延迟、1拍加扰、4拍调制和顶层1拍输出对齐。精确首符号延迟需要仿真。

### 8. 当前没有完整64QAM通路

虽然端口和 bit 聚合器定义了 `QAM64=3`，但 `Modulation.v` 当前只例化 QPSK 和 16QAM，最终 `output_valid` 也只由这两路组成。输入 `modulation=3` 时不会产生有效64QAM输出。上游 `CM_to_PDSCH_Encoder` 目前也只选择 QPSK 或16QAM。

### 9. OFDM触发延迟

- `ENCODE_SAFE_VALUE=20000` 只用于延迟 `OFDM_symbol_trigger_in`，不是整个编码器总 latency。
- 它是固定安全窗口，没有根据编码数据的 `ready/valid` 动态释放 trigger。
- `Trigger_Delay_10x` 当前实际有14个并行触发槽，而不是名字和旧注释中的10个。
- 代码实际计算 `delay-3`，变量名却叫 `delay_minus_2`；`delay<3` 会无符号下溢。
- 下降沿检测的 `else` 后缺少 `begin/end`，公共延迟模块还使用阻塞赋值，因此精确是否延迟 D 拍应由仿真确认。

### 10. 遗留逻辑与集成风险

- `start_of_radio_frame` 支路的下降沿结果没有被任何输出使用。
- `number_of_subframe_latch`、`number_of_subframe_out_reg` 只有声明。
- `number_of_REs_delay1` 虽传入编码器，但编码器内部没有使用。
- `last_sample_in` 被固定为0，结束位置依赖 valid 数量而非显式 last。
- 当前 `TX_BIT_Processor.v` 多处端口连接粘在 `//` 注释后，导致 `MAC_TX.MAC_trigger`、`start_of_radio_frame`、`OFDM_symbol_trigger_out`、`symbol_valid`、`symbol_real` 等连接在 Verilog 语义上被注释掉。
- `PXSCH_Parameter_Computation.v` 也存在 `assign ready_for_configuration` 和 `sync_latch.out` 被同行注释吞掉的现象。

因此必须区分“模块本体设计意图”和“当前工程实际集成状态”。系统仿真前应先确认这些是否为损坏副本并恢复端口换行。

### 11. 反压结论校正

当前可以确认的反压最多到：

```text
TX_Rate_Matcher
→ Turbo_Encoder_Top
→ CRC_Add_and_CB_Segmentation
→ PXSCH_Channel_Encoder.ready_for_data
→ PXSCH_TX_Bit_Processing_Top.ready_for_input
→ MAC_TX.ready_for_output
```

这只能证明 MAC 向编码器的 bit 输出能够暂停，不能直接推出 UDP 写侧一定停写、FIFO 一定不满或端到端绝不丢数据。只有 FIFO 的 `full/almost_full` 真正连回 UDP 源写使能或 ready，才能形成完整写侧反压。
