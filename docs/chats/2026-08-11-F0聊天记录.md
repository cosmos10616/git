## 二、PXSCH_Deserializer_Bit_to_Symbol 精读结论

### 1. 模块本质

该模块不是调制器，也不输出 OFDM/IQ 符号；它只是串并转换器，把速率匹配输出的串行 coded bit 按 Qm 分组为星座标签：

```text
QPSK：每2个有效bit输出1个并行标签
16QAM：每4个有效bit输出1个并行标签
64QAM枚举：每6个有效bit输出1个标签，但当前后级没有真正的64QAM调制器
```

### 2. 关键寄存器关系

- `symbol_out_next` 是正在组装的半成品标签；
- `bit_index` 指示当前输入bit写入bit0、bit1等哪个位置；
- 第一个有效串行bit写入 `symbol_out[0]`，第二个写入 `symbol_out[1]`；
- `bit_index_add1 == bits_per_symbol` 时当前组完成，`valid_out` 拉高一拍，内部组装寄存器和索引归零；
- `valid_in=0` 时索引和半成品保持，所以空拍不计入bit数。

源码使用“比较目标位，若不同则与one-hot掩码异或”的写法：

```verilog
change_flag = symbol_out_next[bit_index] != bit_in;
symbol_out_current = change_flag
                   ? symbol_out_next ^ (6'd1 << bit_index)
                   : symbol_out_next;
```

其功能等价于把 `symbol_out_current[bit_index]` 设置为 `bit_in`。之所以先计算 `symbol_out_current`，是为了在最后一个bit到来的同一个上升沿既包含当前bit又输出完整标签，避免非阻塞赋值导致输出漏掉最后一位。比较、移位和异或的表达方式属于作者编码风格，不是算法必须如此复杂。

当前 `PXSCH_TX_Bit_Processing_Top` 将 `last_sample_in` 固定为0，因此实际只依靠凑满Qm个有效bit结束一组；速率匹配输出G必须能够被Qm整除。

## 三、Gold 加扰与接收端解扰

### 1. 是否每个bit都加扰

算法上每个有效coded bit都执行：

```text
b_tilde(n) = b(n) XOR c(n)
```

RTL已经先把Qm个bit组成并行标签，因此一次并行处理Qm个bit：QPSK一次使用2个Gold bit，16QAM一次使用4个Gold bit。只有标签 `valid_in=1` 时x1/x2状态才向前推进Qm步，空拍不消耗Gold序列。

### 2. c与c_init的区别

```text
c_init：生成x2初始状态的32-bit种子
c(n)：最终Gold序列中的第n个1-bit值
```

当前工程：

```text
c_init = cell_ID | (RNTI << 14) | (subframe_index << 9)
c(n)   = x1(n+Nc) XOR x2(n+Nc)
```

发送端 `Scrambler.v` 以 `data_in ^ x1_state ^ x2_state` 并行完成加扰。

### 3. 接收端为什么也生成c

接收端不会从空口额外接收c，而是使用相同 `cell_ID、RNTI、subframe_index、Qm` 和起始位置重建同一条Gold序列。硬bit情况下再次异或同一c即可恢复原值；当前接收端处理的是LLR软信息，因此：

```text
c=0：LLR保持
c=1：LLR取相反数
```

`Scrambler_Softbit.v` 用 `x1_state_in ^ x2_state_in` 产生控制bit，六个 `Negate_Saturate` 并行决定各softbit是否取负；8-bit最小值-128取负时饱和到+127。发送端与接收端的c若因参数、起始时刻或推进步数不同步，LLR会被错误翻转，后续通常表现为CRC失败。

## 四、PDCCH_Transmitter_Top 图解结论

### 1. 模块定位

当前模块将 `TTI_Handing_Top` 生成的112-bit自定义控制消息编码成3600个QPSK复数符号，提前写入PDCCH符号FIFO，等待资源映射器在子帧0、`symbol_index=8` 读取。

```text
TTI控制消息
→ PDCCH_Transmitter_Top
→ PDCCH symbol FIFO
→ Combine_Control_and_Data资源映射
```

### 2. CM_message结构与串行顺序

```text
[111:88] 无线帧计数器，24 bit
[87:84]  固定子帧数10，4 bit
[83:24]  MCS_array，60 bit
[23:0]   保留0，24 bit
```

`CM_to_Stream` 直接读取 `CM_message[bitindex1]`，索引0到111，因此按LSB first依次发送：保留字段、MCS数组、子帧数量、无线帧计数器。

### 3. 控制流与内部ready

`PDCCH_trigger` 来自无线帧起点，顶层和 `PDCCH_TX_Bit_Processing` 各延迟1拍后启动编码器配置和Gold初始化。`CM_to_Stream` 不由trigger直接启动，而是检测 `PXSCH_Channel_Encoder.ready_for_data` 的上升沿，确认编码器可接收数据后才发送112个串行bit。

### 4. 112 bit到3600符号的数量闭合

`PXSCH_Parameter_Computation` 对 `TBS=112` 查表得到：

```text
C=1
K=136                 // 112信息bit + 24-bit TB CRC
D=K+4=140
Ncb=3D=420
E=7200
k0=8
Qm=2                  // 固定QPSK
```

因为 `E=7200 > Ncb=420`，速率匹配执行大量重复读取而非打孔，平均每个母码bit发送约17.14次。最终：

```text
7200 coded bit / 2 bit每QPSK符号 = 3600个QPSK符号
```

这恰好填满一个OFDM符号的3600个有效子载波。

### 5. FIFO与资源位置

编码后的PDCCH符号以 `PDCCH_valid` 写入 `FIFO_for_PDCCH_symbol`。`Special_Subframe_ChanID` 只在 `subframe_index=0 && symbol_index=8` 产生 `CM_flag`，资源映射器在该OFDM符号的3600个有效子载波拍连续读取PDCCH FIFO。

### 6. 与PXSCH/PDSCH的关系

当前F0工程中，两路复用同一个 `PXSCH_Channel_Encoder`：

```text
PDCCH：112-bit控制消息 → 同一套CRC/Turbo/速率匹配链 → 固定QPSK
PDSCH：MAC成帧后的用户数据 → 同一套CRC/Turbo/速率匹配链 → QPSK或16QAM
```

主要区别是输入内容、是否经过MAC、TBS、调制配置、触发频率和资源位置。当前PDCCH不是标准LTE PDCCH：它使用自定义112-bit `CM_message`、Turbo编码和固定资源位置，而标准LTE PDCCH通常使用DCI、尾咬合卷积码和CCE/REG结构。

## 五、下一个模块：Combine_Control_and_Data

用户确认下一个模块是 `Combine_Control_and_Data`，并询问其是否属于资源映射。

已经明确：从功能上它是资源映射顶层，但实际资源类型判定由内部 `TX_Resource_Mapper_Top` 完成。整体职责包括：

```text
TX_Resource_Mapper_Top判断当前资源类型
→ 根据CM_flag/Data_flag读取PDCCH或PDSCH FIFO
→ 选择RS、PSS或空白数据
→ 组成频域OFDM数据
→ 插入保护带和DC
→ 送入WFRFT/IFFT处理
```

当前工程的映射主要按照整个OFDM符号类型选择，例如子帧0、符号8的全部3600个有效子载波用于PDCCH；它不是标准LTE中在同一OFDM符号内对每个RE进行精细混合映射的完整实现。

### 2. 两个符号FIFO的位置与作用

`FIFO_for_PDCCH_symbol` 和 `FIFO_for_PDSCH_symbol` 都直接例化在 `Combine_Control_and_Data.v` 内，不在PDCCH/PDSCH编码调制模块内部：

```text
PDCCH FIFO：32 bit × 4096，PDCCH_valid写，CM_flag读
PDSCH FIFO：32 bit × 16384，PDSCH_valid写，Data_flag读
FIFO字格式：{imag[15:0], real[15:0]}
```

必须区分两条时间线：`PDCCH_valid/PDSCH_valid` 表示前级现在生产符号；`start_of_symbol` 表示空口资源网格进入新的OFDM符号。FIFO负责把提前生产与按资源位置消费解耦。

### 3. Combine从输入到输出的主线

```text
PDCCH/PDSCH I/Q + valid写入各自FIFO
→ start_of_symbol驱动TX_Resource_Mapper_Top
→ CM_flag/Data_flag读取对应FIFO，RS_flag启动RS发生器
→ 无效通路清零，三路OR得到current_data
→ 248+3600+247形成4095个输入位置
→ DC_Insertion在前2048点后插入一个零，得到4096点
→ WFRFT_TX
→ FFT_valid及输出I/Q
→ TX_BIT_Processor寄存后进入Invalidate_Layer_Streams
```

三路按位OR只在资源类型互斥、未选通路主动清零时等效于多路选择器。FIFO `full` 未接入反压，`empty` 未形成读保护，系统依赖固定调度保证不溢出、不读空。

### 4. 全部直接子模块结论

`Combine_Control_and_Data` 的全部直接子模块已经逐个核实：

1. 三组 `delay_1`：分别对齐WFRFT模式、4095点valid和DC块起点；

### 5. RS保护带结论纠错

此前把左右495个位置一概称为零保护带并不适用于当前全部RTL。`TX_Resource_Mapper_Top` 文件末尾的补丁在RS符号中把 `side_space_delay7` 并入RS使能，所以：

```text
普通PDCCH/PDSCH符号：左右区域不读FIFO，输出零
RS符号：左右区域也可能输出按12层交织后的RS
```

点数仍是 `248+3600+247=4095`，DC仍插在4096点输出的零基索引2048，但RS符号的左右位置不能保证数值为零。`PSS` 类型虽然由资源映射器产生，父模块端口却未连接，当前PSS符号没有实际PSS序列源。

### 6. WFRFT四路结构与当前alpha

```text
X0 = 原序列正序读取
X1 = 4096点FFT结果
X2 = 原序列按(-n) mod 4096循环反序
X3 = FFT结果按(-n) mod 4096循环反序，作为IFFT等效分量
Y  = w0X0 + w1X1 + w2X2 + w3X3
```

当前生效的系数只有：

```text
alpha=10  → 只选择X1（FFT）
alpha=30  → 只选择X3（IFFT等效）
其他alpha → 只选择X0（原序列）
```

完整0～39阶混合系数表已经被注释，活动代码不会混合四路，X2不会被选中。

### 7. FFT等待与反序讨论

`FFT_4096.xci` 已核实为固定4096点、定点、未缩放、`radix_4_burst_io`、`natural_order` 输出。任意一个FFT频点依赖整组4096个输入；该Burst架构按4096个有效输入形成一帧，完成蝶形计算和自然顺序重排后成批输出，核注释延时为10401拍。

FFT结果反序不是纠正IP位倒序，因为IP已经输出自然顺序。它利用DFT性质构造WFRFT的X3：

```text
X1[(-n) mod N] = N·IFFT{x}[n]
```

RAM读取地址为 `0,4095,4094,...,1`，属于循环反序，不是普通的 `4095,4094,...,0`。`WFRFT_Multicarrier` 检测FFT输出valid下降沿，确认4096个FFT结果写完RAM后，再同步正序读X1、反序读X3。

## 九、TX_BIT_FIFO_Exchange精读结果

### 1. 模块定位

该模块接收本FPGA三个 `TX_BIT_Processor` 同步输出的L0/L1/L2复数流，使用 `symbol_valid0` 作为公共有效信号。它不做MIMO矩阵运算，也不跨时钟，而是完成三层并串重排、目标FPGA路由标记和32-to-64 bit打包；输出交给 `FIFO_Manager`，再按目标ID进入本地loopback或三条Aurora分支。

### 2. 数量闭合

```text
每条layer：4096个32-bit复数样点
三条layer：4096×3=12288个32-bit字
两两打包：12288/2=6144个64-bit字
```

`iDataEn` 上升沿经 `enp` 启动12288拍 `long_t4`。总输出有效 `oEn` 为该窗口延迟5拍。

### 3. Layer0旁路与三个FIFO

L1、L2从第一个有效拍起全部写各自32×4096 FIFO。L0最前4个样点走 `oDD3 → 延迟5拍 → oD3` 旁路，第5个样点起才写L0 FIFO；第一次L0读取窗口被 `long_t4d6` 屏蔽，后续才读L0 FIFO。这样补偿FIFO读取启动延迟，并避免最前4个L0样点重复或丢失。

### 4. 重排顺序

0～11循环计数产生三个4拍窗口：

```text
long_t0：输出L0连续4个位置
long_t1：输出L1连续4个位置
long_t2：输出L2连续4个位置
```

因此32-bit串行顺序为：

```text
L0[0..3] → L1[0..3] → L2[0..3]
→ L0[4..7] → L1[4..7] → L2[4..7]
→ L0[8..11] → L1[8..11] → L2[8..11]
```

三组覆盖12个子载波，对应一个RB的本地3层数据：36个32-bit字，打包后18个64-bit字。4096点包含341个完整12位置块和末尾4个位置，模块以固定12288拍精确结束。

### 5. 目标FPGA与64-bit打包

`cntt2` 的case表为：

```text
0→ID2，1→ID1，2→ID3，3→ID0
```

稳定运行时每完成三个4位置小组切换目标ID。当前本板编译 `FPGA_ID=3`，`FIFO_Manager` 将ID3解释为本地loopback，ID0/1/2分别对应Aurora0/1/2。由于起始处还有 `enp/oEn/fpga` 寄存和ID两拍延时，第一个外部有效64-bit字的ID相位需要仿真确认，不能只看case第一项。

`TX_BIT_Data_Processing` 每两个32-bit有效字输出一次：

```text
data_64bit[31:0]  = 前一个32-bit复数样点
data_64bit[63:32] = 当前32-bit复数样点
```

### 6. 代码风险与遗留项

1. 三个FIFO的 `full/empty` 未进入保护，异常断流可能造成零值或层/RB错位；
2. 四路数据通过“无效分支清零后按位OR”选择，依赖读取窗口严格互斥；
3. `long_t3 → sync_latch → out`、`Fpga1`、`long_t4d4` 等未进入有效数据路径，属于遗留逻辑；
4. `iDataEnd1` 实际参与上升沿检测，名字容易误导；`FGPA_ID` 只是 `FPGA_ID` 的拼写错误。

### 2. TX_MIMO_Processor总体功能

当前 `TX_MIMO_Processor` 的实际数据流为：

```text
跨FPGA汇聚后的12层频域数据
→ MIMO_TX_Trigger判断是否可以启动
→ MIMO_Processor_Payload_Reader按四位置小块读出12层
→ TX_Precoding_Direct把12层固定重复为32个天线行
→ Submatrix_Splitter拆成前16根和后16根天线
→ 两个MIMO_TX_Pack_Data把128 bit拆成64 bit
→ 两路MIMO到RRH FIFO
```

当前生效的 `TX_Precoding_Direct` 不执行权重矩阵乘法。它的固定映射为：

```text
天线0～11  ← Layer0～11
天线12～23 ← Layer0～11再次重复
天线24～31 ← Layer0～7再次重复
```

一个128-bit输入字包含4个32-bit复数，即“一条Layer在4个连续位置上的一行”。一个12位置块拆成三组四位置子矩阵；每组读取12条Layer，因此普通块共读取36个128-bit字。

### 3. 两路输出数量闭合

对每个四位置子矩阵：

```text
32根天线 × 每根4个复数
```

F0使用16-bit I和16-bit Q，一个复数32 bit；每个128-bit天线行拆成两个64-bit字。一个完整12位置块有三组四位置子矩阵，因此：

```text
每路：16根天线 × 2个U64 × 3组 = 96个U64
两路合计：96 × 2 = 192个U64
```

`MIMO_TX_Trigger` 的两个容量输入在逻辑上对应这两条输出流。更上层又将每条逻辑流分配到两条物理MIMO到RRH FIFO，因此每条物理FIFO约承载48个U64。当前顶层把两路容量值固定为200，未真正接入FIFO余量；若以后接入真实计数，代码用每一路都大于等于 `U64_PER_RB=192` 判断会比实际每路96的需求更保守，信号语义需要继续核实。

### 4. 四片FPGA从按Layer分工转为按RB分工

BIT阶段每片FPGA生成自己的3条Layer并覆盖全部位置。`TX_BIT_FIFO_Exchange` 与 `FIFO_Manager` 完成分布式转置：交换前是“每片3层的全部块”，交换后是“每片负责部分块，但收齐每块的12层”。

有效全局分配已核实为：

```text
全局内部块 mod 4 = 0 → FPGA1
全局内部块 mod 4 = 1 → FPGA3
全局内部块 mod 4 = 2 → FPGA0
全局内部块 mod 4 = 3 → FPGA2
```

4096个位置形成341个完整12位置块和最后1个4位置块，共342个内部块。FPGA0/2各处理85个，FPGA1/3各处理86个；最后的全局块341由FPGA3处理。

## 十一、MIMO_TX_Trigger精读与问题澄清

### 1. 模块职责

`MIMO_TX_Trigger` 不搬运数据，只决定一个本地RB块能否启动，并产生 `read_payload_trigger`、RB/OFDM符号索引及132拍忙状态。启动条件是：

```text
mimo_enable=1
AND 上游Reader报告数据足够
AND 两路下游容量足够
AND 当前不在处理上一个块
```

### 2. control_flag反馈不是锁存或组合环

`control_flag` 和 `TX_processing_flag` 都经过时钟寄存逻辑。`control_flag`只产生一个启动脉冲，随后 `PULSE_TO_STROBE_U16` 将其扩展成132拍忙状态；忙状态期间 `control_flag`被压低。因此这是同步“启动—忙—完成—再启动”闭环，不是组合环，也不会推断锁存器。

### 3. RB_available_latch为何一直为1

`RB_available_latch` 第一次被置1后保持到全局复位。它只用于产生系统首次有数据时的一次上升沿，启动内部OFDM符号计数时序；后续逐块是否可启动使用另一条 `RB_available_delay4` 路径。因此一直为1不会造成每拍重复触发，但不复位时也不会再次产生新的“首次启动”边沿。

### 4. 12拍、32拍与44拍

每个四位置子矩阵的输入是12条Layer，所以Reader连续读取12拍。当前直接预编码把这12行展开为32个天线行。相邻两组输入起点间隔44拍，普通块的调度为：

```text
[12拍允许读取 + 32拍不发起新读取] × 3 = 132拍
```

输入12拍与输出32拍属于Layer和天线两个不同维度，而且流水线会重叠。44拍的含义是相邻四位置子矩阵的启动间隔，不应解释成输入和输出完全不重叠地严格串行相加。

### 5. RB与OFDM符号概念

标准无线概念中，子载波属于频域，IFFT输出样点属于时域，不能把“一个RB的12个子载波”直接称为12个时域采样点。F0的MIMO链面对4096个复数位置并按12个位置进行内部调度，代码把这种单个OFDM符号内的12位置切片简称为RB；它不是包含一个slot多个OFDM符号的完整二维物理RB。

## 十二、《MIMO 1.1 Manual》与F0工程映射

已重点通读 `MIMO 1.1 Manual.pdf` 的系统架构、数据路由和基站MIMO TX章节，并渲染核查关键图页。可以确认F0明显参考了NI的 `LabVIEW Communications MIMO Application Framework 1.1`，不是仅有模块名相似。

直接对应关系包括：

```text
最多12条空间Layer
单个MIMO Processor面向32根天线
1个RB含12个子载波
每个RB拆成3个“12 Layer × 4 subcarrier”子矩阵
Trigger Generator / Payload Reader / Submatrix Splitter结构
前后半天线拆成两条输出流
多个MIMO Processor按完整RB分担频域数据
```

手册第77页的数据矩阵解释了F0中的数字来源：一个128-bit字是一个Layer的4个连续复数位置；连续12拍收齐一个四位置子矩阵的12条Layer；重复三次覆盖12位置块。

F0的重要改动为：

1. 手册原系统为2048点FFT、1200有效子载波和100个标准RB；F0为4096位置数据链、3600有效子载波和342个内部12位置块；
2. 手册TX使用互易性权重矩阵进行12维复数点积预编码；F0当前例化 `TX_Precoding_Direct`，只做固定重复；
3. 手册说明的原始发送为uncoded transmission；F0加入CRC、Turbo编码和速率匹配；
4. 手册MIMO到RRH接口使用12-bit I/Q特殊打包；F0使用16-bit I/Q并按两个复数一个U64打包。

因此该手册适合用于理解架构、矩阵形状和调度思想，实际位宽、计数范围和算法必须回到F0 RTL核准。

## 十三、MIMO_Processor_Payload_Reader及其子模块

### 1. 父模块的实际作用

`MIMO_Processor_Payload_Reader` 不解析或重排128-bit数据，只完成：

```text
判断FIFO是否足够一个块
→ 按固定节拍发read_fifo
→ 将FIFO返回数据与valid寄存一拍后输出
```

普通块要求 `fifo_number>=36`。FPGA3的本地 `RB_index=85` 是全局最后一个只有4个位置的不完整块，只要求12个128-bit字。

### 2. Payload_Read_Pattern_Generator

该子模块把单拍 `RB_trigger` 展开为读取图样。`PULSE_TO_STROBE_U16`先产生132拍普通窗口或44拍最后块窗口；`Mod_N_Indexer`在窗口内按0～43循环，只有 `rows_index<NUMBER_LAYER=12` 时读FIFO。

```text
普通块：三轮[读12拍 + 停32拍]
总窗口：3 × 44 = 132拍
实际读取：3 × 12 = 36个128-bit字

最后块：一轮[读12拍 + 停32拍]
总窗口：44拍
实际读取：12个128-bit字
```

FIFO顺序必须预先为“子矩阵0的Layer0～11、子矩阵1的Layer0～11、子矩阵2的Layer0～11”；Reader不会检查或重排。触发后图样会完整运行，中途不重新检查FIFO余量，因此假定已预留的数据不会被其他逻辑抢走。

### 3. 数据和延迟关系

`data_out`每拍都寄存 `fifo_data`，后级只能在 `data_out_valid=1` 时使用。源代码说明的总延迟为：

```text
读请求控制路径4拍
+ 外部FIFO固定返回4拍
+ 父模块输出寄存1拍
= 9拍
```

其中FIFO返回4拍不在Reader内部实现；`TX_MIMO_Processor`顶层将 `read_payload_fifo` 延迟4拍后作为 `fifo_data_in_valid`，要求FIFO数据与该固定valid严格对齐。
