## 二、12拍、32拍、44拍和132拍

已经核实并纠正容易误导的说法：

```text
12拍：Reader每拍读取一条Layer，12拍收齐同一组4位置的12条Layer
32拍：该44拍槽剩余时间Reader不再发起下一组读取；后级仍在工作
44拍：相邻两个四位置子矩阵的读取起点间隔
132拍：一个12位置内部块包含3个四位置子矩阵，3×44=132
```

完整Reader图样为：

```text
拍0～11     读位置0～3的Layer0～11
拍12～43    Reader不读
拍44～55    读位置4～7的Layer0～11
拍56～87    Reader不读
拍88～99    读位置8～11的Layer0～11
拍100～131  Reader不读
```

132拍中真正读取36拍，其余96拍Reader不读。这里的44/132是RTL保留的固定调度槽，不是无线协议规定的时长。结合NI原框架可以推断，该调度继承了真实预编码器先收齐12层、再为32天线处理留时间的结构；F0虽使用Direct固定复制，仍保留此调度，因此可能偏保守。

## 三、TX_Precoding_Direct

### 1. 实际功能

该模块没有权重输入，不做复数乘法或求和。它使用彼此相差12拍的三个数据抽头，把12条Layer固定映射为32个天线行：

```text
天线0～11  ← Layer0～11
天线12～23 ← Layer0～11再次重复
天线24～31 ← Layer0～7再次重复
```

输入每拍一个128-bit字，表示一条Layer在4个连续位置上的4个复数；输出每拍一个128-bit字，后级将其解释为一根天线在相同4个位置上的4个复数。

源码把输出注释成18.29格式不成立：本模块没有数学运算或位宽扩展，输出位模式与输入完全相同。上层连线名 `scaled_data`同样不代表真实缩放。

### 2. payload_data_valid纠错

用户指出：纵观当前有效RTL，`payload_data_valid`即使只有一个周期也能完成任务。重新追踪连接后确认该判断正确。

```text
12个128-bit Layer数据仍必须连续传12拍
控制Direct启动只需要在L0处出现一个单拍上升沿
```

`TX_Precoding_Direct`只对 `input_valid`执行 `detect_posedge`，用上升沿启动32拍输出窗口；数据延迟线则无条件每拍移位。因此当前连续12拍valid和仅首拍valid对Direct功能等价，只要L0～L11仍连续无空拍到达。该端口在Direct内部实际更像 `submatrix_start`。

设计风险是：若12条Layer中间断流，即使valid变低，延迟线仍会移位，Layer到天线的映射会错位。

## 四、Reader为什么把read_fifo延迟4拍作为valid

该连接不是反馈读取，而是固定延迟的数据返回对齐：

```text
read_fifo              当前向上游发出读取请求
read_fifo延迟4拍       假定对应128-bit FIFO数据此时返回
fifo_data_in_valid     给返回的fifo_data贴有效标签
data_out/data_out_valid 父模块再一起寄存1拍后交给Direct
```

实际路径包含：`MIMO_TX_Top`先延迟1拍等待源FPGA FIFO编号选择，读取四个64→128位FIFO之一，随后 `FIFO_Manager`根据FIFO真实valid选择并寄存数据。上层没有将真实FIFO valid继续传给Reader，而是假定请求到 `payload_data_in`固定为4拍。

这种设计能工作但对延迟变化敏感；若更换FIFO IP或修改流水线，人工延迟的valid可能与数据错位。更稳健的方案是直接把选中FIFO的真实valid与数据一起传递。

## 五、Submatrix_Splitter

### 1. 实际功能

Splitter接收Direct连续32拍的天线0～31数据，先写入双页RAM，再按以下顺序读出：

```text
A0,A1,A16,A17,A2,A3,A18,A19,...,A14,A15,A30,A31
```

只有一条共享128-bit数据总线：

```text
data_out_0_valid=1 → 当前数据属于A0～A15
data_out_1_valid=1 → 当前数据属于A16～A31
```

连续两个128-bit字表示两根天线各自的4个复数，不是一根天线的8个复数。四个位置保持不变，连续拍在天线维度上移动。

### 2. 为什么一次只有4个位置

一个完整内部块经过Direct后为 `32天线×12位置`。由于总线只有128 bit，而一个复数为32 bit，一拍只能承载一根天线的4个位置。因此分为：

```text
子矩阵0：32天线×位置0～3
子矩阵1：32天线×位置4～7
子矩阵2：32天线×位置8～11
```

三次才覆盖完整12位置块。若一拍传一根天线的12个位置，需要384-bit总线。

### 3. 为什么按前2根、后2根交替

顶层紧接着例化两套Pack：

```text
MIMO_TX_Pack_Data0：接收splitter0_valid，负责A0～A15
MIMO_TX_Pack_Data1：接收splitter1_valid，负责A16～A31
```

每套Pack用连续两个128-bit天线行拼成256 bit，再用4拍输出4个U64。Splitter采用2+2交替，使同一套Pack相邻两组输入起点间隔4拍，正好匹配其4拍输出节奏，并使两套Pack并行工作。

## 六、MIMO_TX_Pack_Data

### 1. 数据转换

每套Pack连续接收两根天线：

```text
第1拍：A0的4个复数，保存到subcarrier_delay1
第2拍：A1的4个复数，与A0拼成{A1,A0}共256 bit
```

随后从低位到高位输出：

```text
U64_0：A0的位置0、1
U64_1：A0的位置2、3
U64_2：A1的位置0、1
U64_3：A1的位置2、3
```

总数据量不变：`2×128 bit = 4×64 bit = 256 bit`。模块只做位宽转换和串行化，不改变复数或天线顺序。

### 2. 为什么需要两个Pack

```text
Splitter持续带宽：128 bit/拍
单个Pack输出带宽：64 bit/拍
两个Pack合计：2×64 = 128 bit/拍
```

只有一个Pack时，32个128-bit天线行需要32拍输入，却需要64拍从一条64-bit通道输出。两套Pack分别处理前后16根天线，每套输出32拍，从而匹配前级持续吞吐并形成两路MIMO到RRH数据流。两个Pack提高的是持续处理能力和并行输出带宽，不是让单个数据的逻辑延迟减半。

## 七、TX_MIMO_Processor总览图与数量闭合

已在 `TX_MIMO_Processor学习.md` 开头增加类似BIT部分的总览：

```text
FIFO_Manager收齐12条Layer
→ MIMO_TX_Trigger调度
→ Payload Reader按三组四位置读取
→ TX_Precoding_Direct固定扩展成32天线
→ Submatrix_Splitter前后16根交替分流
→ 两套Pack转换为两路64-bit FIFO数据
```

一个完整12位置内部块的数量闭合为：

```text
Reader输入：12 Layer×12位置=144个复数=36个128-bit字
Direct输出：32天线×12位置=384个复数
Pack输出：384÷每个U64的2个复数=192个U64
逻辑流0：96个U64
逻辑流1：96个U64
```
