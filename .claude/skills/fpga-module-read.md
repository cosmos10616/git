# F0 FPGA 模块精读

目标：让读者既能形成直观模型，又能把每个结论追溯到当前工程的 RTL。不要把注释、标准协议或历史解释直接当成实现事实。

## 一、证据优先级

按以下顺序建立结论：

1. 当前工程 RTL 的实际赋值、实例化和信号连接。
2. Xilinx IP 的 `.xci`、参数或网表接口。
3. 工程手册、PDF、设计图和测试平台。
4. LTE/5G 标准公式与表格。
5. 根据结构作出的工程推断。

每个重要结论标明证据等级：

- **源码确认**：RTL 或 IP 配置直接证明。
- **文档说明**：工程手册明确说明，但仍应与 RTL 对照。
- **合理推断**：证据支持但源码没有直接写明。
- **待验证**：需要仿真波形、ILA 或设计者说明。

禁止把“合理推断”写成“源码确认”。注释和端口名可能过时，只能作为线索。

## 二、标准精读流程

### 1. 定位模块

先给定位卡片：

```text
模块：XXX
文件：绝对路径及关键行号
实例化位置：谁调用它
上游：数据和控制从哪里来
下游：输出送到哪里
时钟/复位：实际连接到哪个时钟域，复位极性
处理粒度：bit / byte / symbol / RE / sample / code block / TB
```

必须沿实例化连接确认实际时钟。不能因端口名叫 `clk_192M` 就断言频率为 192 MHz。

### 2. 画完整子模块层级树

列出所有功能实例，区分自研 RTL、Xilinx IP、延迟线和调试核：

```text
父模块.v
  ├── 子模块A（第X行）— 输入什么、输出什么、解决什么问题
  │     └── 孙模块A1 — 算法或硬件资源
  ├── 子模块B（第Y行）— 状态机/缓存/地址生成
  └── IP核C（第Z行）— RAM/FIFO/FFT；同时检查IP参数
```

用户问“哪个模块实现的”时，先直接给这棵树，再展开原理。

### 3. 建立端口和单位表

每个关键端口至少说明：

| 信号 | 方向/位宽 | 时钟域 | 单位或粒度 | 有效条件 | 来源/去向 |
|---|---|---|---|---|---|

尤其检查：

- bit、byte、调制 bit、复数 symbol、RE、sample、clock cycle 是否混用；
- 字节内是 LSB-first 还是 MSB-first；
- `valid`、`ready`、`enable`、`full`、`empty` 是否真正构成闭环；
- 输出长度表示单码块、单 TB，还是多个码块总和。

### 4. 先讲直观模型，再讲 RTL 证明

每个模块采用两层解释：

1. **直观层**：一句话功能、数据流图、一个贯穿示例。
2. **RTL层**：关键寄存器、组合逻辑、状态机、地址和有效信号逐一对应。

不要一开始堆协议术语，也不要只讲类比而不回到代码。

### 5. 分开追踪数据路径与控制路径

分别画：

```text
数据路径：输入数据 → 缓存/计算/重排 → 输出数据
控制路径：trigger → 参数锁存 → 状态机/计数器 → valid/ready
```

最后说明两条路径在第几个周期、哪个握手点会合。

### 6. 逐状态、逐周期解释

状态机使用下表：

| 状态 | 进入条件 | 本状态数据动作 | 计数器变化 | 输出/握手 | 退出条件 |
|---|---|---|---|---|---|

选择一个小规模实例贯穿全过程，例如 2 个 payload 字节或短码块，列出周期、状态、地址、数据、valid 和 ready。

检查所有边界：

- 当前值与 `+1` 预判值；
- 非阻塞赋值带来的上一拍/下一拍差异；
- 最后一个元素是否多处理或少处理一拍；
- `ready=0` 时究竟冻结了哪些状态，哪些 FIFO 仍可能写入。

### 7. 区分延迟、吞吐率和忙窗口

看到 `delay_n` 或多级寄存器时，分别回答：

- **延迟 latency**：一组输入多少周期后到输出；
- **吞吐率 throughput**：是否每周期都能接收一组新输入；
- **忙窗口**：接口为何暂时不接受新事务；
- **逻辑路径**：寄存器之间是否真的存在需要分段的组合计算。

纯移位寄存器只增加固定延迟，不能自动解释成“把一段组合逻辑切成 N 段”。若延迟目的没有证据，标记为待验证。

### 8. 验算所有关键数字

先写带单位的公式，再代数值：

```text
13 OFDM-symbol/subframe × 3600 RE/OFDM-symbol = 46800 RE/subframe
62400 coded-bit ÷ 4 coded-bit/16QAM-symbol = 15600 modulation-symbol
```

检查：

- 注释公式是否真的等于宏常数；
- 总量是否已经包含码块数，避免重复乘法；
- 模计数地址的首项、末项和元素个数；
- 固定点缩放应从星座常数反推，例如 Q2.14 使用 16384。

若算术不闭合，先停止推导，不用“流水线开销”“保护间隔”等词补齐差值。

### 9. 区分标准协议与本工程实现

使用三列表格：

| 项目 | 标准协议概念 | F0 当前 RTL 实现 |
|---|---|---|

例如本工程 `MAC_FIFO` 是自定义定长成帧器，不等同于完整 LTE MAC；PXSCH/PDSCH、特殊子帧和公共信道也必须以当前资源映射 RTL 为准。

引用协议章节时说明该公式如何落到具体寄存器、查表值或地址序列。不能只说“协议规定”。

### 10. 处理不确定项

按顺序继续查证：

1. 搜索宏定义及所有赋值点；
2. 追踪上层实例连接；
3. 阅读子模块和 IP 配置；
4. 对照工程手册/PDF；
5. 检查 testbench、ILA 探针或已有波形；
6. 仍不能确认时，列出最小仿真方案和应观察的信号。

不得为了让讲解完整而编造设计动机。

## 三、关键代码引用规则

只引用能证明结论的代码：状态转移、寄存器更新、数据选择、地址计算、握手和延迟对齐。标注文件和当前行号：

```verilog
// 文件名.v 第X行：说明这行证明了什么
关键代码
```

行号必须从当前文件重新获取，不能沿用旧笔记中的行号。

## 四、F0工程常见陷阱

- `Program_Const.vh` 的注释可能与宏值算术不一致；例如 17443 必须保留为待验证，不能自行补成流水线余量。
- 三个 PDSCH trigger 都通过 OR 接到真实输出；不能因为单个 TB 小就断言后两次无效，必须继续追踪每次 trigger 启动的事务。
- FIFO 的 `full` 只有真正连回上游才能形成写侧反压；仅产生 `full` 信号不等于 UDP 会停写。
- 参数相等（如 `E_plus=E_minus`）不代表没有打孔，只代表相应码块输出长度相等。
- 定义了枚举值不代表功能已实现；调制方式必须检查对应实例和输出选择逻辑。
- 两个硬件实例不代表两路数据同时有效；还要检查状态机和各自 valid 区间。
- LabVIEW 风格或相似注释不等于可以断言 RTL 是自动生成的。

## 五、错误校正流程

用户指出矛盾或验算失败时：

1. 明确承认并定位旧结论的位置；
2. 指出具体错在变量、单位、状态定义还是时序拍数；
3. 从复位或已知状态逐拍重算；
4. 给出代数或计数验证；
5. 检查相邻章节是否受同一错误影响；
6. 在笔记原位置加入“校正”说明，不让旧错误继续作为结论传播。

## 六、推荐输出结构

```text
1. 模块定位卡片
2. 一句话功能和直观数据流
3. 输入/输出/单位表
4. 子模块调用树
5. 数据路径与控制路径
6. 每个关键子模块的算法和RTL实现
7. 状态机及逐周期实例
8. 延迟、吞吐率和反压
9. 协议概念与工程实现对照
10. 已确认结论 / 合理推断 / 待验证问题
11. 与上下游衔接及下一学习点
```

对简单模块可以合并章节，但不得省略证据、单位和上下游。

## 七、学习笔记维护

将已经核实的发射端技术内容和有价值的问答整理到项目根目录 `mimo发射端学习.md`：

- 保留详细解释，不为了缩短篇幅删除理解所需的中间步骤；
- 对已经证实的错误结论直接用正确内容替换，不在正文保留相互冲突的旧说法；知识演进由 Git 历史保存；
- 文档按 `MIMO_TX_Top` 直接子模块建立一级标题、内部子模块建立二级标题，并统一包含“实现功能、实现原理解读、子模块关系图、关键代码解读、讨论问题”；
- 不写入密码、API key、访问令牌或其他敏感信息；
- 写入前先检查工作区已有修改，避免覆盖其他工具或用户的内容；
- 写完后核对标题、公式、单位、代码行号和文件总行数；
- 超过 3000 行时建议按模块归档，但须经用户确认；
- 除非用户明确要求或自动化任务规定，否则不自动提交或推送 Git。

## 八、禁止事项

- 不追踪实际连线就根据端口名判断时钟或功能。
- 不检查写使能和反压连接就宣称“不会丢数据”。
- 不验算数字就解释常数来源。
- 不区分 bit、byte、RE、symbol、sample 和 cycle。
- 不贴关键 RTL 就只讲课本原理。
- 不画调用链就直接跳进最底层算法。
- 不用“数学保证”“协议规定”“为了时序”替代证明。
- 不把旧文档、乱码注释或历史对话当作当前 RTL 的最高证据。
- 不在笔记、日志或 Git 中保存任何明文凭据。
